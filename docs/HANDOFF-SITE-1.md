**Decisions I made, and why.** Vercel renamed Edge Config to Global Config while this was built: the site uses the renamed client and reads `GLOBAL_CONFIG`, with the old `EDGE_CONFIG` names still accepted. Aliases with a path segment (`/hub/marketing`, `/hub/results`, `/hub/site`, `/p/01` to `/p/10`) *redirect* to the file instead of rewriting: every page loads its assets by relative path and routes with `location.hash`, so a rewrite breaks them and a `<base>` tag breaks their `#` links. `/`, `/guide`, `/holding`, `/privacy` and `/hub` rewrite as specified. The archive stays as `archive/prototype-01/` (already merged) instead of a tag and branch; `ARCHIVE.md` records it. One line in its `next.config.ts` pins its workspace root to its own folder, because Next.js otherwise took the repository root (the site's lockfile) as the root and tried to build the site's middleware; that is the only change inside the archive. Node 22, not 20: Node 20 is past end of life. The build writes an empty `questions.json` when the sheet has none, which the page treats as "use the built-in questions", so the guide makes no failed request. `shared/dc-site.js` keeps its exact name: two pages find it with a `src$=` selector. Settings are cached 60 s in the middleware as specified, so a switch flipped in Site settings can take up to a minute to show at `/`; the functions read settings at most 5 s old, and a code that is not in the cached list triggers a fresh read, so a new link works within seconds. Private responses are `private, no-store` from the middleware. The middleware asks for the Node runtime; if the deploy refuses `runtime: 'nodejs'`, remove that line, the code runs on the edge runtime too.
